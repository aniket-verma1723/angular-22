Virtual views, stable selection

Concept

Virtual scrolling limits attached DOM, not downloaded records. All 1000 fictional people below already exist locally. No API user data or production table is involved.

Try it

Select person 0001, jump to the last person, select it, then return. Predict the selection count and the number of attached rows. Reset selection without resetting the viewport.

Jump buttons retain focus. Tab into the list; use native scrolling keys on its focusable viewport and Space on a checkbox. No custom arrow-key selection contract.

CDK mechanism

CdkVirtualScrollViewport, the fixed-size strategy and *cdkVirtualFor render 48px rows in a 288px viewport plus buffers. renderedRangeStream reports an end-exclusive range; a post-render DOM read counts attached rows independently.

SelectionModel<string> owns stable IDs outside virtual views; its change stream publishes a read-only signal snapshot. Template caching is disabled here to make destruction obvious.

Common mistake

Checkbox/view identity is not selection storage. Variable row height breaks fixed-size offsets. Virtualizing one remote page neither fetches missing pages nor makes its page-local count a server total.

Revision question

Why can selected IDs outnumber attached checkboxes? Which costs still grow with all 1000 local records?

Test observation

Tests compare a finite row DOM count with the actual CDK range, exercise both jumps, retain IDs across destroyed views, and verify reset and experiment-lifetime boundaries. Virtualization limits browser find and assistive-technology traversal to rendered content; it is not a universal replacement for pagination.
