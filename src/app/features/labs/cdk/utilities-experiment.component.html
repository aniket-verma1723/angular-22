Concept

Direction, focus origin, textarea size and clipboard success are different concerns. Each CDK primitive supplies a mechanism, not a global preference or a guarantee that a browser action succeeds.

CDK mechanism

Dir provides the preview's Directionality and emits dirChange. CdkTextareaAutosize measures content between two and six rows. FocusMonitor.monitor observes the real button; destruction unsubscribes and calls stopMonitoring.

Clipboard.copy returns a boolean. LiveAnnouncer announces the result once per action, while the same visible text has no duplicate live-region role. Its component scope cleans up pending announcements on switching. No HTTP is needed for any experiment.

Common mistake

Copying the current URL can leak query/fragment data. Assuming clipboard success hides browser denial. RTL preview is not translation or a saved application setting. Unsubscribing from FocusMonitor alone does not stop monitoring the element.

Revision question

Why does the scratch direction not affect the toolbar? Why must clipboard failure remain visible even if live announcement fails too?

Test observation

Tests mock the public Clipboard and LiveAnnouncer services, never the OS clipboard. They verify failure/success announcements, local direction outputs, real focus monitoring cleanup, bounded autosize settings and breakpoint teardown. Browser permission and full keyboard/screen-reader audits remain separate.
