Overlay and portal lifetime

Concept

An overlay positions a floating host; a portal supplies its Angular view. Neither supplies a complete dialog workflow. This is a small mechanism experiment, not a replacement for Material Dialog.

Try it

Open help, Tab and Shift+Tab around its two buttons, then close with Escape or the backdrop. Predict where focus returns. Close before using the experiment selector: the modal blocks background interaction. Tests also model navigation away while help is still open.

CDK mechanism

Overlay.create attaches a real TemplatePortal. A global position strategy centers this modal; scrollStrategies.block() prevents page scroll. A connected, nonmodal help popover would instead use a connected position and reposition scrolling.

FocusTrapFactory supplies Tab boundaries. A cancellable afterNextRender performs initial focus. Escape, backdrop and Close dispose the portal, trap and event subscriptions.

Common mistake

Positioning alone is not accessibility. Forgetting disposal leaves listeners alive; an old asynchronous autofocus can steal focus from a newer view. Overlay content inherits root theme tokens, not custom properties defined only on the launching component host.

Revision question

Why block scrolling here rather than reposition? Why must destruction not focus a disappearing trigger?

Test observation

Tests assert portal attachment, labelled dialog, initial focus, both trap boundaries, Escape/backdrop restoration and no stale focus or overlay after replacement/destruction. Full screen-reader review remains manual.
