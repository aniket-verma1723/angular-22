Profiling work versus memoized derivation

Concept

A component being checked is not the same as an expensive calculation being necessary. Compare an expensive template method with a computed value using identical deterministic data and output. The expensive method is an intentional anti-pattern ONLY within this lab, not a recommended application pattern.

The work is capped at 12 fictional samples × {{ rounds }} arithmetic rounds per calculation. Scores are checksums, not timings or real product metrics. There is no random input, I/O, timer, global instrumentation, growing history or signal write during calculation.

Angular DevTools: component and injector inspection

  1. Use a local development build with a compatible Angular DevTools extension already available. Open its Components view and select ProfilingLessonComponent beneath PerformanceLabComponent. If the extension is unavailable, use source inspection and the browser Performance procedure below; no extension is installed by this lab.
  2. Inspect the selected component's state/signals, then operate the note, weight and mode buttons. Look for the changed dependency rather than editing private state from the console. Protected/private TypeScript access is not a security boundary.
  3. Open the Injector Tree view (names vary by extension version), locate the lesson's element injector and inspect its providers/resolution path. ProfilingCalculator comes from this component's providers, not a root singleton. If this view is unavailable, inspect that declaration in the source instead.
  4. Also inspect AnimationLessonComponent and its local AnimationLifetime provider. Show/hide its child to compare the component tree with the Elements panel's leaving host. Do not mistake a visible host for a live instance.

Angular DevTools: repeatable profiling procedure

  1. Wait for unrelated defer/route activity to finish, keep the same data and browser settings, and choose method mode before recording. Warm it up with one note toggle.
  2. Open Profiler, start recording, toggle the unrelated note five times, then stop. Select a relevant change-detection cycle and inspect this component's contribution in the available timeline/flame graph. Save your own trace and label it “method”.
  3. Switch to computed mode, warm it up, and record the same five note toggles separately. The component may still be checked, but unchanged sample data should reuse the computed result. Record the actual durations; do not expect a specific cycle count or speedup.
  4. Make a third recording with one weight toggle in computed mode. The immutable replacement invalidates the dependency, so the next read recalculates. Development verification passes, JIT warm-up and profiler overhead can affect counts and timings. P12's application is Zone-free; Zone.js remains test-only, not a confounder in these application traces.

Browser Performance: verify where time went

  1. Stop the Angular recording. In browser DevTools, open Performance. Keep CPU throttling, viewport, build and data identical for each comparison; note these settings with the trace.
  2. Record the same five note toggles in method mode, then separately in warmed computed mode. Stop each recording. Zoom to an interaction and inspect Main, Call tree or Bottom-up for scripting work; with source maps, look for calculateInTemplate and ProfilingCalculator.calculate. Sampled stacks may miss this small workload.
  3. Compare scripting with style/layout/paint work and the interaction's presentation delay. Reverse the list in a separate trace to study DOM moves. Stable identity avoids replacing rows but does not promise zero layout or paint work.
  4. Repeat runs, preserve the actual traces, and validate user-visible behavior in production output separately. Angular component inspection requires a development build; browser Performance can profile production. Do not compare unlike builds as if only memoization changed.

What Angular does

These components use Angular 22's default OnPush behavior. A handled button event or a changed template signal can schedule a check. OnPush does not memoize arbitrary methods. The method recalculates on template evaluation; computed is lazy and caches its last result until a dependency changes. Reading the unrelated note does not invalidate the sample calculation.

The weight action replaces the array and the changed object; reversal copies before reversing. @for (sample of displayedRows; track sample.id) lets Angular associate each row with a stable ID even when result objects are new. Memoization saves calculation; tracking saves unnecessary DOM replacement. They solve different problems. A pure pipe is another option for argument-based derivation, but this exercise compares a method directly with a computed value.

Common mistake

Do not mutate a signal's array or nested object in place, track reorderable rows by index, increment reactive counters during template evaluation, or manually force change detection to hide a broken update path. Memoization does not make genuinely changed data free: this bounded example recalculates all 12 rows after a weight update or reorder, not just the changed row.

Revision question

Why can the note trigger a component check without another computed calculation? Why can a new array invalidate the calculation while every list element retains its DOM identity?

Test observation

Jasmine spies on the local calculator's public method: note toggles reuse computed work, method mode recalculates, and immutable updates refresh scores. Tests retain actual list-node references to verify stable identity on update and reorder. No production rendering counter is added, so instrumentation cannot schedule a feedback loop.

No profiler results have been collected by this lesson. Call-count assertions prove a mechanism, not a speedup, frame budget, INP score or field Web Vital. Small traces can be noisy; report inconclusive results honestly rather than increasing work until the browser becomes unresponsive.
